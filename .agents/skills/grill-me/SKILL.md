# Grill Me

針對這個 repo 的方案進行嚴格但具建設性的決策訪談，直到與使用者對目標、限制、取捨及驗收方式達成共同理解。

## 開始前

先檢查 repo 內與問題相關的現況。至少在需要時讀取：

- `README.md`：產品目標、候選架構與成功指標
- `PREREQUISITES.md`：M1 16 GB 限制、模型候選、權限與 benchmark 矩陣
- 目前工作樹、既有設計文件或程式碼

可從檔案、工具或其他可用環境取得的事實，直接查證，不要拿來問使用者。只有會改變方案的偏好、優先順序、限制與取捨才交由使用者決定。

## 訪談方式

1. 先找出目前最高層且會影響後續分支的未決問題。
2. 每次只問一個問題，等待使用者回答後再繼續；不要一次列出整份問卷。
3. 每題都提供你的推薦答案，以及一至兩句具體理由或主要取捨。
4. 根據回答更新決策樹，先解決上游依賴，再深入下游細節。
5. 若回答與 repo 現況、硬體限制或先前決策衝突，直接指出衝突並要求選擇，不要默默替使用者決定。
6. 不重問已從 repo 或先前回答確定的事項。

優先盤問會實際影響結果的面向，例如：

- 使用情境、隱私要求與不可接受的失敗模式
- latency、辨識品質、翻譯品質與資源使用的優先順序
- ScreenCaptureKit 擷取範圍與權限體驗
- MLX 與 whisper.cpp 的選擇標準
- Qwen 與 NLLB baseline 的角色、授權與淘汰條件
- partial subtitle 的更新、回改與閱讀體驗
- glossary、測試資料與 benchmark 的 Go／No-Go 門檻

不要為了完整而追問不會改變設計或驗收結果的細節。

## 停止條件

當重要分支都已解決時，先用精簡清單總結：

- 已確認的決策
- 仍保留的假設或風險
- 可驗證的成功／失敗條件
- 下一步建議

接著只問使用者是否確認已達成共同理解。得到明確確認前，不得修改程式碼、文件、設定或執行實作。即使訪談中出現看似明確的實作要求，也先確認訪談結論；確認後才依使用者的新指示行動。
